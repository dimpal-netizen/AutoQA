WHY THIS IS ONE JOB AND NOT {count} JOBS

Failures come in families. Six tests that all fill the same form and all stop at
the same step are one problem, not six — and nobody looking at them one at a
time can tell, because each analysis only ever sees itself. From a real run:

    6 tests red on a registration form
    all 6 stopped at the same modal check
    one cause; one afternoon to fix

Read them together. Say which share a cause, and count how many genuinely
different problems are in front of you. That number is what someone actually
needs — "16 failed" and "16 failed, 3 causes" lead to completely different days.

HOW TO DECIDE, PER FAILURE

Work through these in order — the first that fits is usually right:

1. Did the element not exist, or match nothing? That is `selector_broken`.
2. Did it time out waiting for something that does appear eventually? `timing`.
3. Could the page not be reached at all — connection refused, DNS, 5xx on the
   first navigation? `environment`.
4. Did it use credentials or data that no longer exist? `test_data`.
5. Does it pass in some browsers and fail in others? Say so; that is a strong
   signal of a real, browser-specific application bug.
6. Did the application do something a user would call wrong? `application_bug`.
7. Is the test asserting something that was never true? `test_bug`.

HOW TO WRITE IT

The person reading this is a QA engineer who does not read Python.

- `expected` — what was the test waiting to see? One sentence, in the words of
  someone watching the screen. Not the assertion.
      good: "The one-time-password popup should have closed."
      bad:  "Locator expected to be hidden."
- `actual` — what happened instead? One sentence. These two must genuinely
  disagree; if you are writing the same sentence twice with a "not" in one of
  them, you have not worked out what happened.
- `root_cause` — why. One or two sentences.
- `suggested_fix` — starts with a verb, names the thing to touch, doable today.
  Not "investigate further".
- Plain English throughout. No Python, no Playwright, no class names, no
  `snake_case`, no stack frames.

RULES

- **You are working from text only.** No screenshots are attached to this
  triage, unlike the single-failure analysis. Say what the error, the traceback
  and the steps support, and set `confidence` accordingly — 0.5 or below where
  the evidence is thin. Someone can open one failure for a closer look with a
  screenshot; a confident wrong answer here sends them to the wrong one.
- `same_cause_as` holds the NUMBERS of the other failures sharing a cause. If
  failures 2, 5 and 9 are one problem, all three say so about the other two.
  Leave it empty when a failure stands alone. Do not group failures merely
  because they are in the same file or the same feature — the *cause* has to be
  the same thing.
- `distinct_causes` counts the families, not the failures. Six failures in two
  families is 2.
- Severity is about the impact on the user of the application, not on the suite.
  A broken sign-up is critical; a brittle selector on a cosmetic element is low.
- Set `is_product_bug` true only when the application is at fault. When in
  doubt, it is the test.
- Return exactly one entry per failure listed above, using its number. Do not
  skip one because it looks like another — the reader is matching your answers
  back to their rows.
- Copy that failure's `Test:` name into `test`, exactly as written. It is not
  used to match; it is checked against the row your number chose, and an entry
  whose name does not agree is thrown away. An answer filed against the wrong
  test is worse than no answer, because nothing in it looks wrong.
