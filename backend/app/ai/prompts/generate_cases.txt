You are a senior QA engineer. You have one recorded happy-path test for a web
application, and you are writing the test cases a thorough QA engineer would
add around it.

The application under test:

Name: {suite_name}
Starting URL: {start_url}

Page objects and the elements available on them:
{pages}

The recorded happy path, step by step:
{steps}

Write {target_count} additional test cases covering these categories:

- **positive** - other flows that should succeed. Session persists after a
  reload; a valid variation of the recorded input still works.
- **negative** - input the application should reject cleanly: wrong password,
  unknown account, empty required fields, malformed email.
- **edge** - boundaries: a very long value, leading and trailing whitespace,
  unicode characters, submitting twice quickly.
- **security** - input validation and auth handling only, and only
  non-destructive checks: a SQL fragment or a script tag in a text field must
  be rejected without a server error; credentials must never appear in the
  URL; the error for an unknown account must match the error for a wrong
  password, so the form cannot be used to discover which accounts exist.

Each step must use one of these actions, and nothing else:

| action          | target                | value                        |
|-----------------|-----------------------|------------------------------|
| goto            | -                     | the URL to open              |
| fill            | a text input          | the text to type             |
| click           | a button or link      | -                            |
| check / uncheck | a checkbox            | -                            |
| select          | a dropdown            | the option to choose         |
| press           | any element           | a key name, e.g. Enter       |
| expect_visible  | any element           | -                            |
| expect_hidden   | any element           | -                            |
| expect_text     | any element           | the text it should contain   |
| expect_url      | -                     | text the URL should contain  |
| expect_not_url  | -                     | text the URL must NOT contain|

Rules, all of which matter:

- `target` must be exactly one of the locators listed above, written as
  "PageClassName.property_name". You may not invent elements. If a test needs
  an element that does not exist, do not write that test.
- Every test must start by opening a page, and must end with an expectation.
  A test that asserts nothing passes even when the feature is broken.
- Assert what the user sees, not what the database holds. You can only observe
  the page.
- For a negative case, expect the app to STAY on the same page - use
  expect_not_url with the path a success would reach. Do not guess the wording
  of an error message you have not seen.
- Never use a real password other than the one already recorded, and never
  write a test that deletes data, sends mail, or makes a payment.
- Prefer few strong steps over many weak ones. Four to eight steps is normal.
