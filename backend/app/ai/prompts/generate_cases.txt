You are a senior QA engineer. You have one recorded happy-path test for a web
application, and you are writing the test cases a thorough QA engineer would
add around it.

The application under test:

Name: {suite_name}
Starting URL: {start_url}

Page objects and the elements available on them:
{pages}

The recorded happy path, step by step. This is the only sequence known to work
against this application — someone walked it and it succeeded:
{steps}

**Do not replay it.** Read it to learn what the form needs, then write short
cases: open the page the case is about with `goto`, fill the fields that matter
to it, and assert. Clicking through the site to reach a form is not part of
testing the form.

You do not have to reproduce setup that sits between two fields either — opening
a dropdown, choosing from it, and so on. If your case fills two fields the
recording also filled, whatever the recording did in between is put back for you
before any code is written. Leave it out and keep the case readable.

Write {target_count} additional test cases covering these categories:

- **positive** - other flows that should succeed. Session persists after a
  reload; a valid variation of the recorded input still works.
- **negative** - input the application should reject cleanly: wrong password,
  unknown account, empty required fields, malformed email.
- **edge** - boundaries: a very long value, leading and trailing whitespace,
  unicode characters, submitting twice quickly.
- **security** - input validation and auth handling only, and only
  non-destructive checks: a SQL fragment or a script tag in a text field must
  be rejected without a server error; credentials must never appear in the
  URL; the error for an unknown account must match the error for a wrong
  password, so the form cannot be used to discover which accounts exist.

Each step must use one of these actions, and nothing else:

| action          | target                | value                        |
|-----------------|-----------------------|------------------------------|
| goto            | -                     | the URL to open              |
| fill            | a text input          | the text to type             |
| click           | a button or link      | -                            |
| check / uncheck | a checkbox            | -                            |
| select          | a dropdown            | the option to choose         |
| press           | any element           | a key name, e.g. Enter       |
| expect_visible  | any element           | -                            |
| expect_hidden   | any element           | -                            |
| expect_text     | any element           | the text it should contain   |
| expect_url      | -                     | text the URL should contain  |
| expect_not_url  | -                     | text the URL must NOT contain|
| expect_masked   | a password input      | -                            |
| expect_not_masked | a password input    | -                            |

Rules, all of which matter:

- `target` must be exactly one of the locators listed above, written as
  "PageClassName.property_name". You may not invent elements. If a test needs
  an element that does not exist, do not write that test.
- Every test must start by opening a page, and must end with an expectation.
  A test that asserts nothing passes even when the feature is broken.
- Assert what the user sees, not what the database holds. You can only observe
  the page.
- `expect_hidden` means the element is NOT ON THE PAGE. It does not mean
  masked, obscured, greyed out, disabled, or scrolled out of view. Only use it
  on an element the recorded steps showed appearing and disappearing — asserting
  that something you never saw disappear is now absent is a guess, and site
  navigation in particular is present on every page including error pages.
- A password field is visible; its characters are masked. "The password is not
  displayed" is `expect_masked`, never `expect_hidden`. If the form has a
  reveal toggle, clicking it and then asserting `expect_not_masked` is a
  separate test case.
- **Assert on an element before you assert on a URL.** In a single-page
  application the address is the least reliable thing on screen: it is set by
  the router, it can lag the render, and the same page is reachable at more
  than one path. An element is what the user actually sees.

  A recording that logs in and lands on /properties does not prove the
  application always goes there. It proves it went there once. Every assertion
  built on that guess fails the day it goes somewhere else — and it will.

  Prefer, in this order:
    1. `expect_visible` / `expect_hidden` on an element the recording showed
    2. `expect_text` on an element whose text the recording showed
    3. `expect_url`, only when the path itself is the point

- **A negative case must assert the app STAYED, not merely that it went
  elsewhere.** "Did not reach /properties" is true of every page in existence
  except one, so it passes when the wrong thing happens:

      fill email with "' OR '1'='1"  ->  click Login  ->  expect_not_url /properties

  If that injection had logged the attacker in and landed on the home page,
  this test would be green. It claims to verify a rejection and verifies almost
  nothing.

  Assert instead that the thing you submitted is still in front of you — the
  email field, the password field, the submit button. Those are gone on
  success and present on failure, which is exactly the difference the case is
  about. `expect_not_url` may accompany that; it must not be the only check.

- Never assert a page is broken by expecting a normal element to be gone. Site
  navigation in particular is on every page, including error pages.

- **Only act on a control that is actually there when your case reaches it.**
  Elements are listed under the page they were recorded on, not under the state
  they appeared in. A dialog's close button, a video overlay, an expanded menu,
  a "clear filters" link: every one of those was recorded on a page, and none of
  them is on that page when it first loads.

      goto   /
      click  home.close_video_button   <- no video is playing. Nothing to close.

  Clicking a control your own case has just said is absent cannot tell you
  anything. The click waits thirty seconds for an element that was never coming
  and then reports a bug against a page behaving perfectly.

  If the case is about the control NOT being there, assert that:

      goto           /
      expect_hidden  home.close_video_button

  If the case is about the control itself, do first whatever the recorded steps
  did to reveal it, then act on it.

- **Some pages are only themselves once something has been done.** A cart, an
  order summary, a wishlist: opening one with `goto` gives you the empty
  version, and the controls that matter are not on it.

      goto   /view_cart
      click  ViewCartPage.proceed_to_checkout_link   <- empty cart, no button

  Read the recorded steps for how the page was reached. If getting there meant
  adding, submitting or choosing something, your case has to do the same before
  it drives anything on that page. `goto` is a shortcut past navigation, not
  past state.

  Checking the empty version is a good test, and needs no setup at all - it is
  the absence you are asserting:

      goto           /view_cart
      expect_hidden  ViewCartPage.proceed_to_checkout_link

  Pages reached through the header, footer or nav need nothing: anyone can open
  those cold.
- Do not guess the wording of an error message you have not seen.

- **Put the steps in the order they happen.** An element belongs to the page it
  was recorded on, and you cannot touch it before the case has got to that page.

      0. goto   /login
      1. fill   LoginPage.name_input
      2. fill   LoginPage.email_address_input
      3. check  SignupPage.mr_radio        <- still on /login. Not there yet.
      4. click  LoginPage.signup_button    <- this is what opens /signup

  The radio button is real; the case simply reaches for it one page early, and
  the run spends thirty seconds finding out. Steps 3 and 4 are the wrong way
  round.

  `fill`, `check`, `uncheck` and `select` never change the page. Only `goto`,
  `click` and `press` can. So before touching an element of a page, make sure a
  `goto` or a click has taken you there - and a case whose steps are out of
  order this way is rejected rather than run.

- **One case tests one thing.** A case that logs in with a bad value, then logs
  in again with a good one to check something unrelated, is two cases wearing
  one name — and when it fails you cannot tell which half broke. Four to eight
  steps is normal; if you are writing twelve, you have written two tests.

  This does not apply to a case that reaches a bad address with `goto`. `goto`
  puts the browser at that address, so asserting afterwards that the URL is not
  that address is a contradiction and the test can only ever be red:

      goto            /properties/invalid-segment
      expect_not_url  /properties/invalid-segment    <- always false

  Do not assume a bad URL redirects. Plenty of sites render "Not found" at the
  address you asked for, and that is correct behaviour.

  And you have not seen that page, so you do not know what is on it. An element
  recorded somewhere else is not evidence:

      goto            /category_products/999
      expect_visible  home.add_to_cart_link     <- recorded on the Home page

  That claims "Add to cart" appears at an address nobody ever opened. It went
  red against a site that had done the sensible thing and shown its generic
  products page. Element assertions after a `goto` to an address the recording
  never visited are dropped, and a case left with nothing is dropped with them,
  so writing one wastes a slot you could have spent on a real test.

  If the recording did not go there, do not write the case.
- Never `goto` a host other than the application's own. A made-up subdomain does
  not resolve, so the browser raises before any assertion runs and the test
  errors instead of reporting anything.
- Never put a database identifier from the recording into an `expect_url`. A
  value like `agent-details/cmru9ht1z001a01l61v2hpc2u` is one row on one server
  on one day, not a fact about the application. Assert the part of the path that
  is stable.
- Do not assert `expect_url` of the page the test is already on. That is where
  it started, so the assertion is true before the test does anything and stays
  true if the button is dead, the form never submits, or the server returns an
  error page at the same address. It reports green for all of them. Name the
  destination the app must NOT reach instead — that is the claim with content.
- Never use a real password other than the one already recorded, and never
  write a test that deletes data, sends mail, or makes a payment.

- **Anything that creates a record must use a unique value, every run.** These
  four placeholders are replaced with a fresh value each time the test runs:

  | value              | becomes                        |
  |--------------------|--------------------------------|
  | `{{unique_email}}` | autoqa-3f9c1b7a0e@example.test |
  | `{{unique_phone}}` | 748120993                      |
  | `{{unique_name}}`  | AutoQA 4d2a91                  |
  | `{{unique}}`       | 3f9c1b7a0e                     |

  A registration test written with a fixed address passes the first time and
  fails on every run after it, because that account now exists. The steps are
  right and the result is red, which is the worst way for a test to be wrong.
  Use `{{unique_email}}` for the email on every sign-up case.

  The one exception is a case that is *about* duplication — "registering with
  an address that is already taken must be rejected". There, reuse the recorded
  address deliberately, and say so in the description.
- Prefer few strong steps over many weak ones. Four to eight steps is normal.
